# System Architecture — Milestone 1

## Purpose
This document describes the implemented Milestone 1 foundation for AI Project Intelligence & Risk Advisor. It covers ingestion, retrieval-augmented generation (RAG) preparation, and vector indexing only.

## High-level architecture
```text
PDF / DOCX / CSV / TXT
        |
        v
React + Vite upload interface
        |
        v
FastAPI upload endpoint
        |
        v
Format-specific text extraction
        |
        v
Text normalization and overlapping chunks
        |
        v
Sentence Transformers embedding function
        |
        v
ChromaDB persistent collection
        |
        v
Semantic retrieval endpoint -> React results
```

## Component responsibilities
- **React UI:** upload files, display indexing outcomes, list indexed documents, submit a semantic search query, and display retrieved text chunks.
- **FastAPI:** validate file extensions, invoke extraction, chunk the text, add chunk documents and metadata to ChromaDB, and expose status/search/delete endpoints.
- **Ingestion module:** extract text from PDF, DOCX, CSV and TXT. It reports basic file-specific metadata.
- **Embedding function:** `all-MiniLM-L6-v2` through ChromaDB's Sentence Transformers embedding function. The model is downloaded on first use.
- **ChromaDB:** persist vector embeddings and metadata under `backend/data/chroma_db`.
- **Tests:** exercise TXT and CSV extraction, invalid/empty file handling, and chunk generation.

## RAG workflow
1. A user uploads supported project artifacts.
2. The backend extracts text and basic metadata.
3. Text is normalized and divided into overlapping character chunks.
4. ChromaDB's embedding function generates vectors for each chunk during insertion.
5. ChromaDB stores vectors, text, and metadata persistently.
6. A search query is embedded and compared against stored vectors; the API returns matching chunks and source labels.
7. The UI displays retrieved passages so the user can inspect the source content.

This milestone demonstrates document preparation, indexing, and retrieval. It does not generate a synthesized answer with an LLM.

## Document data model
Each indexed chunk stores:
- `id`: unique ID composed from the upload document ID and chunk index
- `document_id`: ID for the uploaded file
- `source`: original file name
- `file_type`: pdf, docx, csv, or txt
- `chunk_index`: zero-based chunk order
- `document_metadata`: serialized metadata from extraction
- `document`: extracted text for the chunk
- `embedding`: vector generated by the embedding function

## Design limitations
- Text-based PDFs are supported; scanned PDFs without a text layer are not OCR-processed.
- Chunk boundaries are character-based and try to prefer word boundaries.
- There is no user authentication, multi-tenant isolation, cloud deployment, or production upload security.
- No later-milestone agents or project-health logic are implemented.
